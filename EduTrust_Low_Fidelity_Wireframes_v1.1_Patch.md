# 3. Patch 1 — Add P-14A / P-22A Late Payment After Expiry

## Finding closed

`LFW-AUD-001 — Late payment after expiry lacks explicit dedicated screen/state variant`

## Patch decision

Add explicit low-fidelity screen/state variant:

```text
P-14A / P-22A — Late Payment After Expiry / Reconciliation
```

This screen appears when provider success arrives after the booking can no longer be fulfilled.

## New wireframe state variant

```text
[Payment received after reservation expired]

Payment status: Received
Booking status: Reservation expired / cancelled
Session status: Not scheduled

Your payment was received after the reservation expired, so the session was not confirmed.
A refund/reconciliation process has been started.

[View refund timeline]
[Choose another slot]
[Contact support]
```

## Screen specification

| Field | Specification |
|---|---|
| Screen ID | P-14A / P-22A |
| Actor | Parent |
| Purpose | Explain late payment after booking expiry without implying fulfillment |
| Entry point | Payment Pending polling, Payment History, Booking Detail, notification |
| Preconditions | Payment confirmed after booking became `EXPIRED` or `CANCELLED`; booking is unfulfillable |
| Primary content | Payment received; reservation expired; no session scheduled; refund/reconciliation started |
| Secondary content | Booking summary, payment reference, refund timeline link |
| Primary CTA | View refund timeline |
| Secondary CTA | Choose another slot; Contact support |
| Disabled actions | View session, Review teacher, Retry old booking, Reassign slot |
| State badges | Payment received, Reservation expired, Refund/reconciliation started |
| Loading state | “Checking payment and refund status…” |
| Empty state | Not applicable |
| Error state | Could not load reconciliation status; show support link and safe refresh |
| Permission-denied state | Parent can view only own payment/booking/refund |
| Relevant API endpoint(s) | `GET /payments/:id`, `GET /bookings/:id`, refund timeline source defined in Patch 4 |
| Backend state represented | `payment.status = CONFIRMED`; `booking.status = EXPIRED/CANCELLED`; no session; refund/reconciliation exists |
| Event generated by action | Backend emitted `PAYMENT_CONFIRMED`, `PAYMENT_RECONCILIATION_REQUIRED`, refund lifecycle events |
| Idempotency requirement | Read-only; refund command idempotency handled by backend |
| Navigation destination | Refund Timeline, Teacher Availability/Search |
| Sensitive-data visibility rules | No raw provider payload; no other parent slot/booking details |

## Forbidden UX in this branch

Do not show:

```text
Booking confirmed
Session scheduled
Teacher payout pending
Review teacher
Retry booking confirmation
```

## API contract dependency

The booking/payment response must expose an unfulfillable late-payment status summary, for example:

```json
{
  "payment_status": "CONFIRMED",
  "booking_status": "EXPIRED",
  "fulfillment_status": "UNFULFILLABLE_LATE_PAYMENT",
  "session_id": null,
  "refund_status": "REQUESTED"
}
```

This is not a new state machine. It is a response representation of the already-approved late-payment branch.

# 4. Patch 2 — Sensitive Admin Access Must Audit

## Finding closed

`LFW-AUD-002 — Sensitive admin access still uses “may audit” wording`

## Patch decision

Replace all sensitive-access wording of this form:

```text
may audit
may generate audit/security event
may itself audit depending policy
```

with:

```text
must generate ADMIN_ACTION and/or SECURITY_EVENT according to access type
```

## Screens patched

| Screen | Previous issue | Replacement rule |
|---|---|---|
| P-06 Student Passport v0 | “sensitive teacher/admin access may audit” | Teacher/admin sensitive access must be audited where sensitive data is accessed |
| T-43 Student Session Context | “sensitive access may generate audit/security event” | Sensitive student context access must generate audit/security event according to policy |
| A-49 Booking Monitoring | “sensitive drilldown may audit” | Sensitive drilldown must be audited |
| A-51 Refund Queue | “sensitive access may audit” | Sensitive refund/payment access must be audited |
| A-60 Event Ledger | “sensitive access to event detail may itself audit” | Sensitive event detail access must be audited |
| A-61 Security Events | “sensitive viewing may audit” | Security event viewing must be audited according to role/policy |
| A-64 Audit Trail | “sensitive audit access may audit” | Sensitive audit trail access must be audited |

## Updated universal wording

For ordinary non-sensitive reads:

```text
Ordinary list read does not require Event Ledger.
```

For sensitive drilldown:

```text
Opening sensitive details must generate ADMIN_ACTION and/or SECURITY_EVENT according to access type.
```

For admin UI warning:

```text
This access will be logged.
```

## API contract dependency

Admin endpoints that return sensitive information must create audit/security records server-side. The frontend warning is informational; it is not the audit mechanism.

## Backend authority

- ADMIN: audited sensitive access.
- OPS: limited audited sensitive access.
- SUPPORT: restricted/redacted access unless explicitly authorized.

# 5. Patch 3 — A-59 Recovery / Adjustment Backend Authority

## Finding closed

`LFW-AUD-003 — Admin recovery/adjustment CTA lacks explicit backend command authority`

## Patch decision

For MVP low-fidelity wireframes, **A-59 becomes read-only**.

Remove/hide the CTA:

```text
[Create adjustment]
```

until a concrete backend command authority is specified in the implementation API plan.

## Updated A-59 wireframe

```text
[Recovery / Adjustment]
Original paid payout
Refund reference
Teacher recoverable
Platform absorbed amount
Future payout offset
Adjustment status
[View ledger/audit]
[View refund]
[View payout]

No manual Create Adjustment button in MVP wireframe.
```

## Updated screen specification

| Field | Updated specification |
|---|---|
| Primary CTA | View ledger/audit |
| Secondary CTA | View refund; View original payout |
| Disabled actions | Create adjustment hidden; editing old payout disabled |
| Backend state represented | Adjustment/recovery entries created by RefundService/PayoutService/LedgerService as side effect of approved post-payout refund workflows |
| Event generated by action | Read-only view: none unless sensitive drilldown; sensitive drilldown must audit |
| Idempotency requirement | Not applicable for read-only screen |

## Backend authority rule

Post-payout recovery remains architecturally required, but the low-fidelity screen does not expose a manual admin create action.

Approved behavior:

```text
Paid payout + later refund
→ Refund/Payout/Ledger service creates adjustment/recovery as part of controlled financial workflow
→ A-59 displays it
```

Forbidden behavior:

```text
Admin manually edits old payout
Admin manually creates arbitrary adjustment without approved command authority
```

## API contract dependency

A-59 requires read access to adjustment/recovery summaries through payout/refund/admin finance responses.

If future implementation needs manual exceptional adjustment, it must first define an explicit audited, idempotent admin command. That is outside this low-fidelity patch.

# 6. Patch 4 — Canonical Refund Read / Admin Refund Data Source

## Finding closed

`LFW-AUD-004 — Refund/admin refund-read endpoints remain partly implementation-dependent`

## Patch decision

Use a canonical hybrid approach:

### Parent-facing refund data

Parent refund timeline is read through existing parent-owned resources:

```text
GET /payments/:id
GET /bookings/:id
GET /disputes/:id
```

These responses must embed refund summaries/timelines when refund activity exists.

### Admin/OPS refund operations

Admin/OPS refund queue/detail uses explicit admin refund endpoints:

```text
GET /admin/refunds
GET /admin/refunds/:id
POST /admin/refunds/:id/reconcile
```

This is an API contract clarification for the already-approved `refunds` lifecycle. It is not a new MVP feature.

## Parent response expectation

`GET /payments/:id` must provide:

```json
{
  "payment_id": "pay_123",
  "payment_status": "PARTIALLY_REFUNDED",
  "refunds": [
    {
      "refund_id": "refund_123",
      "status": "PROVIDER_PENDING",
      "refund_type": "PARTIAL",
      "requested_amount": "400.00",
      "approved_amount": "400.00",
      "currency": "DZD",
      "reason": "Partial refund approved after dispute resolution.",
      "created_at": "2026-09-05T15:00:00Z",
      "approved_at": "2026-09-05T15:10:00Z",
      "provider_submitted_at": "2026-09-05T15:12:00Z",
      "completed_at": null,
      "failed_at": null,
      "rejected_at": null,
      "cancelled_at": null
    }
  ]
}
```

## Admin response expectation

`GET /admin/refunds/:id` must include:

```text
refund lifecycle fields
payment/booking/dispute references
requested_amount
approved_amount
teacher_adjustment_amount
platform_adjustment_amount
provider_refund_id, redacted if needed
reconciliation summary
provider event summary
admin audit references
```

Raw provider payload is not returned by default.

## Wireframe screens affected

- P-22 Refund Timeline
- P-24 Refund Rejected
- P-25 Refund Cancelled
- P-26 Refund Completed
- A-51 Refund Queue
- A-52 Refund Detail
- A-53 Refund Reconciliation

## Patch decision

Use canonical scoped booking endpoint:

```text
GET /bookings?scope=teacher
```

Do not use `GET /teacher/bookings` as canonical in low-fidelity wireframes.

## Screens patched

- T-31 Teacher Dashboard
- T-34 Booking Requests / Bookings

## Updated endpoint references

Replace:

```text
GET /teacher/bookings or GET /bookings scoped
```

with:

```text
GET /bookings?scope=teacher
```

or implementation equivalent where auth role automatically scopes the result.

## Backend authority

Teacher receives only bookings where:

```text
booking.teacher_id = authenticated_teacher.id
```

Teacher cannot view unrelated parent/student booking data.

# 8. Patch 6 — Availability Block / Unblock Endpoint Names

## Finding closed

`LFW-AUD-006 — Availability block/unblock endpoints are not named explicitly`

## Patch decision

Name block/unblock endpoints explicitly in T-33.

## Updated endpoint references for T-33

```text
POST /teachers/availability/rules
PATCH /teachers/availability/rules/:id
POST /teachers/availability/slots
POST /teachers/availability/slots/:id/block
```

```text

SLOT_BLOCKED
```

# 10. Patch 8 — Account / Security Read API Contract

## Finding closed

`LFW-AUD-008 — Account/security screens depend on incomplete session/security read APIs`

## Patch decision

Define implementation-level read expectations for account/security screens.

## Canonical endpoints

```text
GET /auth/sessions
GET /account/security-events
POST /auth/logout
POST /auth/revoke-sessions
```

## Required session response fields

`GET /auth/sessions` should return:

```text
session_id
device_label
created_at
expires_at
last_used_at, if available
is_current_session
revoked_at
approximate_ip_or_region, if policy allows
```

Do not expose raw tokens or refresh token hashes.

## Required security event response fields

`GET /account/security-events` should return user-visible security events such as:

```text
password changed
login failed threshold
session revoked
suspicious activity notice
```

Admin-only security details remain in admin security events.

## Screens patched

- P-28 Account / Security
- T-45 Account / Security

## Backend authority

- Parent/teacher can read own auth sessions and own user-visible security events.
- Admin security event access remains under Admin screens and must be audited where sensitive.

## Idempotency requirement

`POST /auth/revoke-sessions` should be safely repeatable/recommended idempotent.

# 11. Patch 9 — P-15 Payment Success Error Copy

## Finding closed

`LFW-AUD-009 — P-15 “support/retry” wording should avoid implying retriable mutation`

## Patch decision

Replace unsafe wording in P-15.

## Previous wording

```text
Payment confirmed but session missing should not occur; show support/retry status if detected.
```

## Corrected wording

```text
Payment confirmed but session missing should not occur.
If detected, show automatic status refresh and support escalation.
Do not show retry payment, retry booking, or retry session creation to the parent.
```

## Updated P-15 error state

| Field | Updated specification |
|---|---|
| Error state | “We are verifying your booking confirmation. If this does not update shortly, support will review it.” |
| Disabled actions | Retry payment disabled; retry booking disabled; session action disabled until backend state is consistent |
| Navigation | Support/contact and safe refresh only |

## Related architecture rule

Webhook confirmation must atomically create:

```text
payment CONFIRMED
booking BOOKED
session SCHEDULED
```

A stable missing-session state is an operational incident, not a user-resolvable action.
